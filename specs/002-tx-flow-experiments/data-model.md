# Data Model: `txflow` file formats

Formats for the artefacts in [`spec.md`](./spec.md): experiment spec, graph IR,
manifest, schedule and results, plus the chain context materialise reads. All
human-edited files are YAML; machine-written files are JSON or JSON Lines. Field names
are `snake_case`. Every file carries `version: 0` until the format is declared stable.

## 1. References and names

| Form | Meaning |
|---|---|
| `wa` | a **source**: an abstract funding output declared in `sources` |
| `a1.0` | output 0 of transaction `a1` |
| `chains/a1` | transaction `a1` emitted by pattern instance `chains` |
| `chains/a1.0` | output 0 of that transaction |

Transaction, source, wallet, validator, policy and pattern-instance names match
`[a-z][a-z0-9_]*`. A pattern instance namespaces every name it emits with `<id>/` when
its `count` is 1, and with `<id>_<k>/` (k = 0, 1, …) when its `count` is greater than 1.
Labels, target names and the experiment name are free strings; none of them is written
into transaction metadata (§4). A reference that does not resolve is an error (FR-005).

## 2. Graph IR

The IR is the contract between expansion, import, materialisation and (later) sim-rs.

**Inputs are the primitive.** A transaction lists the outputs it spends and the outputs it
only reads. Conflicts, orphans and reference contention are never declared; they are
derived from those lists (below).

```yaml
version: 0
wallets: [alice]               # symbolic owners; bound to keys at materialise time
validators:                    # optional; scripts that outputs can be locked to
  <name>: { kind: always_succeeds, budget: { mem: <u64>, steps: <u64> }, size: <u32> }
policies:                      # optional; minting policies
  <name>: { kind: signed_by, wallet: <wallet> }   # native script, wallet signature
sources:
  <name>: { owner: <wallet>, lovelace: <u64> }
txs:
  <name>:
    inputs: [<ref>, ...]               # spent; ordered, order preserved in the built tx
    reference_inputs: [<ref>, ...]     # read only; optional
    collateral: <ref>                  # required iff an input is locked by a validator
    mint: { <policy>.<asset>: <i64> }  # optional; negative burns
    outputs:
      - to: <wallet> | script:<validator>
        lovelace: <u64> | min | change # exactly one `change` per tx (default: last output)
        tokens: { <policy>.<asset>: <u64> }   # optional
        datum: { bytes: <u32> } | { inline: <cbor-hex> }   # optional
        pad_bytes: <u32>               # optional, inflates tx to a target size
    template: { file: <path>.tx3, tx: <name>, args: { ... }, hash: <blake2b256> }  # optional (story 5)
    validity: { from_slot_offset: <i64>, ttl_slots: <u64> }  # optional, relative to replay start
    labels: [<string>, ...]
```

Spending an output locked by `script:<v>` uses validator `<v>`'s execution budget for
that input's redeemer, so a batch transaction that spends a pool output and several order
outputs uses each one's validator. Built-in validator kinds (`always_succeeds` with a
target size and budget) are generated by `txflow`; their code hash is fixed per kind and
parameters.

**Derived relations** (computed by `txflow`, written to the canonical IR, never hand-edited):

```yaml
derived:
  topo_order: [chains/a1, chains/b1, chains/a2, chains/b2, chains/a3, chains/b3]
  conflict_sets:            # spend/spend: ≥2 txs list the same output in `inputs`
    chains/c1: [chains/a1, chains/b1]
    chains/c2: [chains/a2, chains/b2]
  reference_contention:     # spend/read: one tx spends what another only reads
    pool/p0: { spent_by: [pool/batch1], read_by: [pool/quote3] }
  orphan_on:                # tx → conflict sets among its ancestors; it is invalid if its ancestor loses
    chains/a2: [chains/c1]
  hash: blake2b256:<hex>
```

**Rules**

- Every input, reference input and collateral is a named reference, so the materialiser
  never selects coins (FR-011).
- Two `reference_inputs` entries on the same output are not a conflict.
- A transaction may belong to several conflict sets (it spends several contested outputs)
  and may be both in a conflict set and orphaned by an ancestor's conflict.
- `change` absorbs the remainder after fees, explicit outputs and minted value; a negative
  remainder, or a token output not covered by inputs plus `mint`, is an error naming the tx.
- Canonical form: keys sorted, maps sorted by name, no YAML anchors, integers as integers.
  The hash covers everything except `derived.hash`, including validator definitions and
  each template's `hash` (the blake2b-256 of the `.tx3` file, filled in at expand time), so
  editing a template or a validator changes the IR hash (FR-006).

## 3. Experiment spec

```yaml
version: 0
experiment: <name>
seed: <u64>
params: { <name>: <number|string> }    # referenced as {{ name }} in pattern args
wallets:
  <name>: {}                            # MVP: all wallets bind to one key
validators: { ... }                     # optional, same schema as §2
policies: { ... }                       # optional, same schema as §2
patterns:
  - id: <instance-name>
    use: <pattern>
    count: <expr>                       # instances to emit, default 1
    with: { <arg>: <expr> }
txs: { ... }                            # optional explicit IR txs, same schema as §2
sources: { ... }                        # optional explicit sources
schedule: { ... }                       # see §5
expect: [ ... ]                         # see §7
```

`<expr>` is a number, a `{{ param }}` substitution, or simple arithmetic over params
(`{{ pairs * scale }}`). No conditionals or loops: anything richer belongs in a pattern.

**Scaling is explicit.** `scale` is an ordinary param with no built-in meaning. A spec
scales by referencing it in `count` or in a pattern argument (`users: "{{ 50 * scale }}"`).
Patterns never read params the spec did not pass them, so a value cannot be applied twice.
Scaling `count` gives more independent copies; scaling an argument such as `users` gives
more contention inside one instance.

### Pattern catalogue (MVP)

| Pattern | Emits | Arguments |
|---|---|---|
| `independent` | `n` unrelated single txs | `n`, `ins`, `outs`, `size` |
| `chain` | `t1 → … → tN` | `length`, `ins`, `outs`, `size` |
| `fan_out` | one tx with `width` outputs, each spent by a child | `width` |
| `fan_in` | `width` txs whose outputs one tx spends | `width` |
| `conflicting_chains` | chains `a` and `b` | `length`, `conflict: root \| per_step \| every_k`, `k` |
| `conflict_set` | `k` txs spending one source | `k` |
| `diamond` | fan-out, parallel chains, fan-in | `width`, `depth` |

After script support: `order_batch` (`users`, `orders_per_batch`, `batches`, `validator`)
and `contended_state` (`contenders`, `rounds`, `validator`). Both generate `collateral`
sources for every script spend.

## 4. Chain context and manifest

### Chain context (input to materialise)

Materialise performs no network I/O. It reads a chain-context file:

```yaml
network: { magic: 164, era: dijkstra }
pparams: <path to protocol-parameters JSON>      # e.g. from a node query or db-sync
funding:
  key: <path to payment signing key>
  utxos: ["<txid>#<ix>", ...]                      # with their values
  values: { "<txid>#<ix>": { lovelace: <u64> } }
```

How the file is produced (a one-off node query, Ogmios, db-sync, or a future net-rs N2C
client) is outside the format. `txflow context` may offer helpers.

### Run key

All sources are paid to a **run key** derived from the funding key, the IR hash and the
seed, never to the funding key's own address. Other tools using the funding key, and other
`txflow` runs, therefore cannot spend an experiment's sources between `fund` and `replay`.

### Manifest

Written by `txflow materialise`. JSON. Contains no wall-clock data.

```json
{
  "version": 0,
  "run_id": "9c41e07a2b5d13f0",
  "ir_hash": "blake2b256:…",
  "seed": 42,
  "network": { "magic": 164, "era": "dijkstra", "pparams_hash": "blake2b256:…" },
  "wallets": { "alice": { "run_key_vkey_hash": "…" } },
  "funding": [
    { "tx_id": "…", "cbor": "…", "spends": ["<txid>#0"], "sources": { "chains/wa": 0, "chains/c1": 2 } }
  ],
  "txs": {
    "chains/a1": {
      "index": 0, "tx_id": "…", "cbor": "…", "size": 312, "fee": 171265,
      "inputs": [ { "ref": "chains/wa", "utxo": "<txid>#0" }, { "ref": "chains/c1", "utxo": "<txid>#2" } ],
      "conflict_sets": ["chains/c1"], "orphan_on": [], "labels": ["side-a"], "pattern": "chains"
    }
  }
}
```

- `run_id` is the first 8 bytes (hex) of blake2b-256 over `ir_hash`, `seed`, `pparams_hash`
  and the sorted funding UTxOs, so the same inputs give the same `run_id` (FR-012).
- `funding` is a list: one funding transaction per at most `funding_outputs_per_tx` sources
  (default 200, chosen to stay well under `maxTxSize`), chained so later funding txs spend
  earlier ones' change. All are built offline with the rest of the graph.
- Transaction metadata (FR-013), label `1023` (proposed; must not collide with
  tx-firehose's `1022` colour label), holds only fixed-size values:
  `{ 0: <8-byte IR hash prefix as bytes>, 1: <8-byte run_id as bytes>, 2: <tx index as uint> }`.
  The manifest maps `index` back to the symbolic name, so names of any length are safe.

## 5. Schedule

Part of the spec, or a separate file passed to `txflow replay`.

```yaml
schedule:
  releases:
    - select: { label: side-a }       # or { names: [a1, a2] } or { pattern: chains }
      target: relay-tokyo             # name resolved through `targets`
      via: n2n                        # n2n | n2c
      at: 0ms                         # offset from replay start
      spacing: 0ms                    # between consecutive selected txs, in topo order
    - select: { label: side-b }
      target: relay-frankfurt
      via: n2n
      at: 0ms
  targets:
    relay-tokyo: { host: "10.0.1.5:3001" }
    relay-frankfurt: { host: "10.0.2.5:3001" }
    node1-socket: { socket: "node1/node.socket" }
  options:
    skip_descendants_of_rejected: false   # takes effect only for n2c releases
    observe_for: 120s                     # how long to watch for on-chain inclusion
```

A transaction matched by several releases is submitted by each. A transaction matched by
none is not submitted (a warning lists them). `trigger:` is reserved for event-based
release (out of scope for now). The schedule has its own canonical hash, recorded in
results next to the IR hash: two runs are comparable only if both match.

## 6. Results

`results.jsonl`, one JSON object per line. `t_ns` is monotonic from replay start;
`run_start` anchors it to wall-clock time and slot.

```json
{"t_ns": 0, "event": "run_start", "run_id": "…", "ir_hash": "…", "schedule_hash": "…", "seed": 42, "network": {"magic": 164, "era": "dijkstra", "pparams_hash": "…"}, "start_utc": "2026-10-12T14:03:11.204Z", "start_slot": 3061391, "txflow": "0.1.0", "targets": {"relay-tokyo": {"node_version": "…"}}}
{"t_ns": 1203400, "event": "offered", "tx": "chains/a1", "tx_id": "…", "target": "relay-tokyo", "via": "n2n"}
{"t_ns": 1350950, "event": "body_requested", "tx": "chains/a1", "tx_id": "…", "target": "relay-tokyo"}
{"t_ns": 1450210, "event": "rejected", "tx": "chains/b1", "tx_id": "…", "target": "node1-socket", "via": "n2c", "reason": "…"}
{"t_ns": 9800000000, "event": "on_chain", "tx": "chains/a1", "tx_id": "…", "slot": 3061401, "block": "rb|eb", "block_hash": "…"}
{"t_ns": 120000000000, "event": "outcome", "tx": "chains/b2", "result": "lost_conflict", "conflict_set": "chains/c2", "also": ["orphaned"]}
{"t_ns": 120000000000, "event": "run_end", "expectations": [{"id": "one_per_conflict", "pass": true}]}
```

What each transport can report:

| Transport | Events |
|---|---|
| N2N TxSubmission | `offered` (tx id announced), `body_requested`. The peer's mempool decision is not sent back, so there is no `accepted` or `rejected`. |
| N2C LocalTxSubmission | `accepted`, or `rejected` with the node's reason |
| Observation (db-sync or node logs) | `on_chain` with slot and RB/EB |

At the end of `observe_for`, every submitted tx gets one `outcome`: `included`,
`lost_conflict` (another member of one of its conflict sets landed), `orphaned` (an
ancestor did not land), `lost_reference` (an output it reads was spent first), or
`not_seen`. A tx can carry more than one cause in `also`.

## 7. Expectations

```yaml
expect:
  - id: one_per_conflict
    each_conflict_set: { on_chain: exactly_one }
  - id: a_side_fast
    select: { label: side-a }
    on_chain_within: 40 slots           # from the tx's own submission, via start_slot
  - id: no_split_block
    each_conflict_set: { same_block: never }
```

## 8. Import (story 4)

`txflow import --db <postgres-url> --address <addr>... --slots <from>..<to> --fidelity shape|values|scripts`
writes a spec containing explicit `txs`, `sources`, `validators`, a `schedule` reproducing
relative arrival times, and, where fitting succeeds, a commented-out equivalent `patterns`
entry. Role assignment: the script address becomes `script:<n>`; each distinct payment
key becomes `user_<n>` in first-seen order; a key that spends three or more script
outputs in one tx is labelled `batcher`.

## Worked example

The P1 experiment: a1→a2→a3 and b1→b2→b3, each aᵢ conflicting with bᵢ.

```yaml
version: 0
experiment: conflicting-chains
seed: 42
wallets: { alice: {} }
patterns:
  - id: chains
    use: conflicting_chains
    with: { length: 3, conflict: per_step }
schedule:
  releases:
    - { select: { label: side-a }, target: node1, via: n2n, at: 0ms }
    - { select: { label: side-b }, target: node2, via: n2n, at: 0ms }
  targets:
    node1: { host: "127.0.0.1:3001" }
    node2: { host: "127.0.0.1:3002" }
expect:
  - { id: one_per_conflict, each_conflict_set: { on_chain: exactly_one } }
```

It expands to:

```yaml
sources:
  chains/wa: { owner: alice, lovelace: 10000000 }
  chains/wb: { owner: alice, lovelace: 10000000 }
  chains/c1: { owner: alice, lovelace: 2000000 }
  chains/c2: { owner: alice, lovelace: 2000000 }
  chains/c3: { owner: alice, lovelace: 2000000 }
txs:
  chains/a1: { inputs: [chains/wa,   chains/c1], outputs: [{ to: alice, lovelace: change }], labels: [side-a] }
  chains/a2: { inputs: [chains/a1.0, chains/c2], outputs: [{ to: alice, lovelace: change }], labels: [side-a] }
  chains/a3: { inputs: [chains/a2.0, chains/c3], outputs: [{ to: alice, lovelace: change }], labels: [side-a] }
  chains/b1: { inputs: [chains/wb,   chains/c1], outputs: [{ to: alice, lovelace: change }], labels: [side-b] }
  chains/b2: { inputs: [chains/b1.0, chains/c2], outputs: [{ to: alice, lovelace: change }], labels: [side-b] }
  chains/b3: { inputs: [chains/b2.0, chains/c3], outputs: [{ to: alice, lovelace: change }], labels: [side-b] }
```

Derived: conflict sets `chains/c1: [a1, b1]`, `chains/c2: [a2, b2]`, `chains/c3: [a3, b3]`;
`orphan_on` lists `c1` for a2 and b2, and `c1, c2` for a3 and b3. With `conflict: root`
only `c1` would exist, and the later txs would appear only under `orphan_on`.

If a1 and a2 land, b2's `outcome` is `lost_conflict` (via `c2`) with `also: [orphaned]` (b1 lost).
To scale to ten independent pairs of chains, add `count: 10`; names become
`chains_0/a1` … `chains_9/b3`.
