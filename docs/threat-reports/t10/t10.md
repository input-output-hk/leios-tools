# Threat T10: Decline to vote, ver. 1.1 (final)
Red Team, IO|Labs <br>
August-November, 2026

## Abstract

Threat T10 corresponds to behaviour where some nodes decline to 
vote for Leios blocks (while still participating in other node 
protocols and activity). This may lead to reduced EB certification 
and, as a result, to effectively disabling the Leios protocol.
The behaviour may be malicious, although the honest variant (when
nodes are misconfigured or disabled due to technical problems)
is also possible.

It is expected, however, that the whole blockchain will remain functioning
(maybe with throughput reduced), if this attack is not combined with other
attacks.

The result of experimentation supports this claim: when this situation
was reproduced, the network remained stable.

## Experimentation

If protocols are properly implemented, then there is no question that the
T10 attack will not touch the Praos protocol. However, the protocol
implementation can be vulnerable to this attack (due to implementation
bugs). So, the main issue here is to check the implementation in a 
real network, in a setting when more than 25% of nodes do not vote for EBs.

This condition was observed during the deployment of test instance of Haskell 
Cardano Leios node to the Musashi testnet. In the initial state right after 
the deployment, the BLS keys configuration (needed for Leios voting) was
omitted from the initial deployment.
After a while, when more pools with stake have registered, the 75% voting 
threshold was no longer being met. This is the so-called 'stake dilution'.
During this period almost no EBs got certified, but Praos blocks proved to 
be added to the blockchain.
After adding BLS keys to test node instance, the test node started voting and 
therefore 75% threshold limitation was fulfilled. EB blocks started 
to be certified immediately.

The experiment was not deliberately planned. This condition was observed
during regular work with the Musashi testnet. Freshly registered stake pools
were not properly configured with block-producing and voting nodes, which
effectively led to a T10 attack.

### Discussion

One can see the following difference in stats under attack as compared to normal:

* Certified EB count: 2 EBs (barely accepted) instead of 72/69 (so, Leios voting was effectively blocked).

* Tx rate per slot: dropped 3 times without Leios quorum (12.9 instead of 43.2/37.9).

* Praos block count per slot: slightly increased (6%, 24.549 slots per block vs 25.972/25.939 slots per block
  in case of normal functioning). The effect resembles that in previous experiment, but relatively
  small --- maybe statistical artifact.

The network remained stable and no other problems (in addition to reduced throughput) were found.

## Results

Without Leios quorum (when nodes are misconfigured and refuse to vote for EBs), 
the network seems to be stable and the performance corresponds to typical Praos level.

A slight increase in praos block rate per slot under T10 attack is observed (possible testing/statistical artifact).
