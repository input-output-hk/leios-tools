T20 scenarios
==============

The following scenarios were tested on net-rs cluster and here are
the results of the experiments.

Honest scenario
----------------

Let's depart from "honest" scenario for T20 ("honest" withholding of transactions): 
a node is very efficient in tx production, but it's very slow in distributing txs to
the network: so it announces EB with new TXs, not known to anyone yet. How strong
is the performance impact on the network?

### Honest scenario emulation

Let's block TX submission protocol for "our" transactions (that is, transactions
generated by current node), but leave LeiosFetch (Bitmap) protocol for fetching
TXs after the moment of EB publication. This is effectively the most extreme case
of the "honest" scenario.

### Test results

In case of network diameter 3, 4 + 50-300 ms ping delay: almost no impact on EB 
certification, but may reduce TX throughput. At diameter 5 the whole EB protocol
does not work even without T20/adversarial actions with these delays (1500 ms).

*Preliminary conclusion*: A challenge to protocol, but protocol may withstand this.
Real-life scenarios are not so extreme (TX submission protocol will work anyway,
at least to some extent).

Adversarial scenarios
----------------------

Let's see actual limitations for the network stability. So, we need to add some
adversarial component.

### Option 1: block TX submission protocol for all transactions

No transactions are transmitted through TX submission (not only "ours", but
any received by the node from outside).

Fetch performance is not enough with 50-300 ms delays for normal EB functioning
in any environment.

### Option 2: block TX submission protocol for all TXs, but for P% of nodes

For each diameter there is a proper % of transactions, which still allow EBs
to be produced. Performance is heavily influenced (3-5 times throughput drop).

### Test results

#### Experiment 1.

As low as 12% of nodes, blocking TX submission protocol, can affect performance 
and reduce reliability/throughput of the node.

This result is achieved with single LeiosNotify/LeiosFetch pair.
Original implementation of LeiosFetch in Piranha Node does not try to request
transactions from a peer again.

So, typical scenario looks like this:
1. Leios Txs Offer from a Peer (inbound; LeiosNotify message);
2. Leios Txs Request from the Peer (LeiosFetch);
3. Leios Block Txs Response from the Peer;
4. No further requests from the Peer.

However, Leios Peer may issue Txs Offer immediately after it received at least
one of the transactions --- and in 1-2-3 slots it could receive more Txs, 
but the Node will not request Txs again from the Peer (point 4 in scenario above).

#### Experiment 2.

The LeiosFetch algorithm was modified. Now it repeats LeiosFetch each slot,
until it downloads all the data. Ldiff + Lvote = 7 (in basic scenario), so
this should work up to diameter=7.

In this scenario 100% of adversarial nodes with blocked tx-submission still
give 90%-100% validation of the blocks (diameter=3, 25 nodes)

### Most obvious remedy

Reduce diameter of the network: if a peer does not actively participate in TX 
submission (does not effectively distribute TXs), reduce the peer's rating and
try to select another (better) peer.

Appendix. T20 raw test results
===============================

Test environment:
* 25 nodes, equal stake, degree 5, diameter 3, 50-300 ms delay between nodes;
* T20 attack

Test results:
1. Filtering only "ours" txs -- no impact on EB cert, reduces TX throughput
2. Filtering all txs (effectively no Tx shipping at all) -- no certs of EB
3. Filtering all txs on 32% of nodes -- some certs, drop in TX throughput; 40% -- no certs, 24% of nodes -- no impact

Test environment:
* 25 nodes, degree 2, diameter 10, 50-300 ms delay between nodes;

Test results:
1. network at the edge of disintegration: EB slowly cease to distribute only Praos works)

Test environment:
* 25 nodes, degree 3, diameter 4, 50-300 ms delay between nodes;

Test results:
1. Filtering only "ours" txs -- small impact on EB cert (80-90% of approval), reduces TX throughput, 
2. Filtering all txs on 20% of nodes -- at the edge of performance
